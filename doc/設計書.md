# 依存関係に基づくデプロイ計画のプロトタイプ

## 目的

10以上のAWSリソースを対象に、変更されたリソースとその依存先を特定し、依存関係を守って順番にデプロイする。

リソース数に応じて親ワークフローやPythonコードに分岐を追加せず、リソース定義ファイルを追加・更新して拡張できる形を目指す。

## ファイルと責務

### `.github/deploy/dependency.yml` — リソース定義と依存関係

リソースごとに次の情報を定義する。

- `paths`: 変更検知の対象となるファイルやパスパターン
- `depends_on`: 先にデプロイする必要があるリソース
- `workflow`: そのリソースを実際にデプロイするワークフロー
- `template`: CloudFormationを使う場合のテンプレートパス

依存関係と変更パスの正本はこのファイルとする。リソースの追加時に、親ワークフローや計画生成コードへリソース名を追加する必要はない。

### Pythonの計画生成 — 変更検知と順序解決

GitHub Actionsランナー上でPythonを実行し、次を行う。

1. コミット差分から変更ファイルを取得する
2. `dependency.yml` の `paths` と照合して、変更されたリソースを特定する
3. 変更されたリソースが依存するリソースを再帰的に計画へ含める
4. 依存グラフをトポロジカルソートし、デプロイ順を決める
5. 実行計画を `deploy-plan.json` として出力する

循環依存、未定義の依存先、重複依存など、誤った定義は計画生成時にエラーにする。

### `deploy-plan.json` — 今回の実行計画と結果

計画生成処理が実行ごとにランナー上で生成する。変更リソース、依存先を含むデプロイ順、各ステップで使うワークフローやテンプレートを記録する。

共通の実行処理がJSONを先頭から読み、各ステップのワークフローを順番に起動して完了を待つ。失敗時は後続のステップを起動せず、状態と実行IDをJSONに記録する。

実行後のJSONはGitHub Actionsの成果物として保存する。依存関係の正本はJSONではなく `dependency.yml` とする。

### リソース別デプロイワークフロー — 実際のAWS操作

各リソースのAWS操作は、そのリソース定義に記載したワークフローが行う。親ワークフローと計画実行処理は個々のリソース名を分岐条件にせず、計画JSONに記載されたワークフローを動的に起動する。

リソース間でAWS操作やパラメーターが異なる場合、その差は各リソースのデプロイワークフロー側に置く。共通化できる操作が増えた段階で、共通デプロイワークフローにまとめられる。

## 全体の流れ

```text
GitHub push
  → Pythonがコミット差分を確認
  → dependency.ymlから変更リソースを特定
  → 依存先を含めて対象を統合
  → 依存順に並び替え
  → deploy-plan.jsonを生成
  → 共通実行処理がJSONを順次実行
  → 成功・失敗と実行IDをJSONに記録
  → JSONを成果物として保存
```

## 拡張方法

新しいリソースを追加するときは、原則として次を行う。

1. デプロイワークフローを用意する
2. `dependency.yml` に変更パス、依存先、ワークフロー、必要ならテンプレートを追加する

変更検知・依存解決・並び替え・順次実行の共通処理は、リソース数に応じた分岐を追加せずに利用する。
